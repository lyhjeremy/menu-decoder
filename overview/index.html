Local LoRA fine-tune with a layered allergen guard

A guard around a 1.5B allergen tagger takes false-safe calls from 7.3% to 0.8%

Menu Decoder reads a photographed menu, translates each dish, and tags it for cuisine, 14 EU allergens, spice and diet. The tagger is Qwen2.5-1.5B with a LoRA adapter that writes the whole tag set as JSON from a prompt as short as Dish: Pad Thai. Claude given that prompt describes the dish instead. Claude given the full schema catches more allergens than the fine-tune does, and misses fewer outright.

So the tagger now sits behind two more layers that can only add warnings: an ingredient lexicon and a Claude Haiku second opinion asked about the allergens still marked "not indicated". On 60 dishes built to hide an allergen, the misses go from 22 to 0, for $0.18 per 1,000 dishes and more warnings.

Guardrails, added 2026-11-13

Two cheap layers behind the tagger, measured on held-out and adversarial dishes

The fine-tune's misses were the reason to build a guard. Each layer reads the same dish text and can only raise an allergen call (not_indicated to may to contains), never lower one, so a layer can only remove false-safe calls and the price is extra warnings. The question was how many of each.

L1LoRA taggerThe fine-tune as benchmarked above. On the held-out set its saved outputs from training/bench_tagger.py are reused; on the adversarial set it was run again on this machine (Apple M4), model loaded once.
L2Ingredient lexiconsrc/allergen_lexicon.py: 541 ingredient, sauce, stock and technique words in English and the menu languages, each mapped to its allergen (tahini to sesame, dashi to fish, moules to molluscs, a wine reduction to sulphites). No dish names, by rule. Matching folds accents and runs in 0.04 ms a dish.
L3Second opinionsrc/allergen_guard.py: Claude Haiku is shown each dish with the allergens still not_indicated and asked which ones its standard recipe usually or often has. Ten dishes per call. The reply must pass a pydantic schema and an id check, gets one retry, and if that fails every open allergen becomes may.

The adversarial set (eval/guardrails/adversarial_set.json, frozen in commit 51c4ae3 before any guard run) is 60 dishes whose name or description never says the allergen: Moules Marinières, Tremoços, 蚝油芥兰, a Caesar salad, a ragù with its soffritto and wine. I drafted it with a model from standard recipes, one recipe note per dish; nobody has checked the labels by hand. Pick a dish to see what each layer did.

Error analysis: what each layer caught, and what it cost

Lexicon catches
Translated ingredient words the LoRA read past: gambas (crustaceans), calamares a la romana (molluscs), marisco, tonnato (fish), shorshe (mustard), nogada (nuts), and both lupin dishes, tremoços and altramuces. 11 of the 22 adversarial misses.
Haiku catches
Recipe knowledge that a word list cannot hold without naming dishes: anchovy in a Caesar dressing, tahini in hummus, walnuts in a Waldorf, almonds and sesame in mole poblano, celery in gumbo and minestrone, the egg wash on tonkatsu. The other 11.
Misses left
Held-out, two slots: eggs in 陳皮欖角蒸鯪魚球, dace fish balls whose description lists no egg, and mustard in undhiyu. Both labels come from the synthetic generator and are arguable; neither layer flagged them.
Run to run
Three Haiku runs on the adversarial set agreed on 484 of 514 open allergen slots (94.2%). Run 3 cleared Hummus of sesame, so the hidden false-safe rate across runs was 0.0%, 0.0% and 0.8%. One run is not enough to trust the zero.
False alarms
The lexicon maps the Thai word kung (shrimp) and so warns about crustaceans on Kung Pao chicken. Haiku added 22 warnings on slots labeled not indicated, most of them "stock may contain soy" (coq au vin, bordelaise, risotto) or "frying oil may be peanut oil" (calamares).
A draft label that is wrong
Haiku called eggs contains on chiles en nogada because the chiles are often battered (capeados). The draft label says not indicated. Haiku is probably right, which is why the set ships with eval/guardrails/labeling_sheet.csv, 840 rows for a person to check.
Harness bug
On the first adversarial run Haiku copied the example id d1 for every dish in two of six batches, both retries failed, and the fail-closed fallback warned on everything. The request now numbers dishes d1 to d10 (commit 6fdaf67); the bad run is kept in outputs/superseded/.
Sonnet instead
As the second opinion, Sonnet also reached 0 hidden misses, but over-warned on 32.2% of slots and cost $0.0021 a dish, 12 times Haiku.

One caveat on the lexicon's adversarial number: the same agent wrote the lexicon and the adversarial dishes, so its 11 catches there are optimistic. The held-out result (30 misses down to 17) is the cleaner measure of the lexicon, and Haiku never saw any label.

What I would do next

  • Have a person fill in the labeling sheet, then rescore; the chiles en nogada row already says some labels will move.
  • Count the usability cost directly: how many dishes each layer removes from a diner's safe list, per allergen.
  • Run the second opinion five times on the adversarial set and flag a slot if any run flags it, to see whether the hummus miss goes away and what it does to over-warning.
  • Fold Haiku's flags back into the LoRA's training data, so the cheap local model learns the hidden allergens itself.
  • Test on photographed menus, where the dish text comes out of OCR and is messier than any synthetic prompt.

Benchmark

Why Claude has two rows

Given only Dish: X., Claude answers a different question, "tell me about this dish". It returns valid JSON 94% of the time, but under its own keys (region, main_ingredients, flavor_profile), none of which match the scored fields, so its allergen scores are zero by construction. The second row appends src/decoder.py's tagging rubric and a description of the output format, with no examples and no answers. With that, Claude beats the fine-tune on allergens.

The fine-tune's case is narrower. The 14-allergen contract lives in its weights, so the prompt can be one line, and it runs locally with no per-call cost. It also gets cuisine right 99.3% of the time against Claude's 81.0%.

Per allergen

Close on the common allergens, behind on the rare ones

An average hides the dangerous cases, so the benchmark scores each allergen on its own. Switch to false-safe to see where the fine-tune tells a diner a dish is clear when it is not.

Molluscs is the worst result: the fine-tune tagged 39.1% of mollusc dishes "not indicated", and peanuts follow at 18.2%. Sulphites and celery show 0% recall with no false-safes, which means the fine-tune never said contains for either; it said may, a warning without confidence.

Fail-safe design

The app can warn about an allergen but never clear one

The tagger misses allergens, so the app around it assumes it will. Three layers push every decision toward a warning, and two of them are plain code the model cannot override.

01Tagging rubricAnswer may whenever an allergen is plausible in a typical preparation: sesame oil in many Asian dishes, gluten in most sauces and breading. "When uncertain, prefer may over not_indicated."
02Badge rendererALLERGEN_BADGE in src/safelist.py maps contains to a cross, may to "ask the staff" and not_indicated to an open circle. It has no entry for a check mark.
03Safe-list filterfilter_safe_dishes removes every dish marked contains or may for any of the diner's allergens, and any dish that fails a stated diet or spice limit, before the recommendation call. The model picks from what is left.

The cost of layer 03 shows up when you run it over the fine-tune's own tags for the 303 test dishes. Pick allergens below and see how much of the menu survives.

The filter is doing what it was built to do, and this is what it costs. For gluten the filter leaves nothing, for sulphites 31 dishes, and for soy or sesame fewer than half the menu. A diner with one of those allergies gets few or no recommendations and a menu of "ask the staff" badges. Lines the vision step can't read stay on the menu, flagged as unreadable, rather than disappearing.

Training

6,750 synthetic dishes, split by dish family

scripts/gen_dishes.py generated 6,750 rows with claude -p: 15 cuisines, 150 dishes each, three prompt variants per dish (name only, name with description, original script with translation, such as ผัดไทย (Pad Thai)). The three variants of a dish always share a split, so the model can't memorize a dish from one variant and get credit on another. Row IDs are hashes, so training/prep_tagger.py rebuilds the generator's item list to recover each row's family: 2,250 families, 6,096 train, 351 validation and 303 test rows, leakage check passing.

Training used MLX on Apple Silicon: batch 4, 12 LoRA layers, 800 iterations, learning rate 1.5e-4, sequence length 768, set after measuring a median target of about 204 tokens.

Limitations

Labels from Claude, no human check yet

The adversarial set's labels were drafted by a model too, from the recipe notes in the file, and the agent that drafted them also wrote the lexicon. eval/guardrails/labeling_sheet.csv lists all 840 dish and allergen slots with blank reviewer columns for a person to fill in.

Every label in the benchmark was generated by Claude, and Claude is also one of the systems being scored. The spec requires a human spot-check of about 60 dishes stratified across cuisines; it has not been done. Until it is, the Claude rows measure agreement with Claude's own labels, and every figure here is about synthetic data.

The first Claude run was contaminated. claude -p ran inside the repo, and 8 of the first 100 answers read the training code to find the schema. Turning tools off made it worse: answers turned into narrated tool calls. Running the CLI from a scratch directory outside the repo fixed it, and the rerun showed no contaminated answers.

The LoRA path in the app was broken at first too. It parsed mlx_lm.generate's raw output, which wraps the JSON in a banner, and expected a dish_id the model never produces, so every call fell back to the default. Both are fixed, and the 25 tests pass. This is not a medical device; confirm allergens with restaurant staff.
